状态更新（2026-09-20）：空树同步已独立实施，结果见 [空树同步交付](EMPTY_SYNC_2026-09-20.md)。方案评估后用户接受取消网页气泡并授权实施权限收敛，代码与自动化验证已完成，真实环境限制见 [权限交付](HOST_PERMISSIONS_2026-09-20.md)。凭证与 KDF 仍为未实施方案。前批修复见 [接手修复结果](FIX_RESULTS_2026-09-19.md)。架构与流程仍分别以 REFACTORING.md、AGENTS.md 为准。

建议按“权限收敛 → 可选会话解锁 → KDF 两阶段升级”分批实施，每批独立验收。权限收敛不改变云端格式；会话解锁先解决凭证落盘及后台暂停语义；KDF 最后协调多设备读写兼容。下文保留原条目编号。

| 优先顺序 | 建议范围 | 收益与主要代价 | 实施前产品决定 |
| --- | --- | --- | --- |
| 1：权限 | 按目标申请主机权限，移除全网页提示脚本 | 缩小网页访问范围；首次连接需授权 | 接受取消网页内完成气泡，保留角标与面板日志 |
| 2：凭证 | 增加可选会话解锁，升级用户默认仍持久保存 | 减少所选秘密持久落盘；重启后需解锁才能后台同步 | 先为 E2E 主密码提供选项；连接凭证是否同批纳入 |
| 3：KDF | 先读新旧格式，再显式切换新格式写入 | 提高离线猜测成本；旧客户端无法读新格式 | 全部设备可协调升级，且低性能设备实测可接受 |

## 2. 凭证存储升级（建议第二批）

代码事实：连接凭证及 E2E 主密码保存在 `storage.local`；`encryption-migration.ts` 的待迁移记录也保存下一份 E2E 设置，包括主密码。`crypto.ts` 的派生密钥缓存以明文口令与 salt 拼接作键，最多保留 8 项。设置页、`useActiveStorage`、后台状态读取及同步层都有凭证消费者，不能只改设置页。

平台事实：`storage.session` 在内存中保存数据，可跨后台 worker 重启，但浏览器重启会清空；Chrome 的扩展重载、更新或禁用也会清空。默认不向内容脚本开放。Chrome 的 `storage.local` 默认可供内容脚本访问，可用 `setAccessLevel` 收紧；不能据此假设 Firefox 提供相同方法。[Chrome storage 文档](https://developer.chrome.com/docs/extensions/reference/api/storage)、[Firefox session 文档](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/session)。

建议新增可选“本次浏览器会话解锁”，保留升级用户原有持久保存默认值。最小首批先处理 E2E 主密码；WebDAV 密码和 Gist Token 是否一起会话化独立决定。会话模式减少持久落盘，不防御已被攻陷的扩展运行环境，也不保证历史磁盘副本或 JS 字符串被物理擦除。

实施边界及顺序：

1. 复用现有配置读取入口统一解析秘密来源，明确区分“未配置”“已锁定”“可同步”；覆盖 UI 与后台，不能在缺少会话秘密时偷偷回退到 local。
2. 仅在没有运行中写入或待处理迁移时切换保存策略。先写入并核对 session，再更新策略与清除 local 秘密；清除失败不能显示为保护已完成。每步可重试，配置与迁移记录中的秘密均须核对。
3. 待迁移记录只持久保存非秘密的目标、候选路径、摘要、基线、阶段和提交状态；所需密码留在 session。重启后重新输入所需密码，校验后继续或取消；不能因缺密码丢弃恢复记录。
4. 锁定应等待运行中的写入安全结束，随后一并清除会话秘密及派生密钥缓存。E2E 保持开启，不能自动改传明文。后台定时任务暂停，保留离线待上传及 ACK 状态，解锁后对账补传。
5. 导入导出继续默认排除秘密；显式导出秘密须已解锁，说明现有 Base64 配置文件不是加密容器。目标切换不能沿用另一目标的凭证。日志与测试不写入真实秘密。

暂不引入 OS 密钥链：扩展与本机程序通信需要额外 native host 及安装注册安排，当前仓库没有这条部署链路；本轮没有验证 OS 存储实现。[Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)。

验收：Chrome/Firefox 的浏览器重启、后台重启、扩展重载/更新、解锁和锁定、目标切换、定时任务、离线补传、迁移中断恢复、导入导出；检查 local 普通设置和嵌套迁移对象均无所选会话秘密，锁定后缓存被清空。同步更新中英文隐私说明。

## 3. 主机权限收敛（已按后续授权实施）

以下保留获确认的实施方案及其决策依据；当前实现与验收以 [权限交付](HOST_PERMISSIONS_2026-09-20.md) 为准。取消气泡已获明确接受，无需重复决策。

代码事实：两个 manifest 都要求 `<all_urls>`，并静态注册覆盖 HTTP/HTTPS 网页的完成提示内容脚本；`sync-indicator.ts` 向各窗口活动页发送通知。Gist API 可自定义；原始文件 URL 校验允许 `gist.githubusercontent.com`、配置的 API 主机，以及默认 GitHub API 场景下的 `raw.githubusercontent.com`。因此不能仅列三个固定域名，也不能只改 host_permissions 就声称完成收敛。

建议移除静态全网页提示脚本及其发送路径，保留扩展角标与面板日志；用户需要自定义 WebDAV/API 地址，manifest 可声明广泛的可选主机范围，但运行时只申请当前目标所需范围。声明可选范围不等于已经获得全部授权。主机授权不能宣称等同于 WebDAV 单目录访问隔离。[Firefox optional_host_permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/optional_host_permissions)、[Match patterns](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Match_patterns)。

实施边界及顺序：

1. 从校验通过的目标计算所需主机，设置页保存、测试、创建等按钮的用户操作中请求授权，再交给后台处理。Chrome `permissions.request` 要求用户手势；后台闹钟不得尝试弹授权窗。[Chrome permissions](https://developer.chrome.com/docs/extensions/reference/api/permissions)。
2. 拒绝授权保留旧连接配置及当前草稿，不发起新目标写入。Gist 遇到受信任但未授权的下载主机时暂停，并提供显式授权按钮；不可信 raw URL 直接拒绝，不把它转成授权请求或发送 Token。
3. 后台每次操作检查授权，撤销权限时暂停并给出可操作提示，保留待同步、ACK、基线和恢复状态。换域时重新计算，避免跨目标使用旧凭证。
4. 升级时核对实际已有授权与旧全网授权的移除结果，不能假定改 manifest 就自动撤销历史授权。只移除本扩展已无用途的授权，失败时明确状态。

第一批不新增可选网页提示框架；如果必须保留网页内气泡，应重新评估所需网页访问范围后再实施。

验收：Chrome/Firefox 新装及升级、首次拒绝、撤销与重新授权、换域、HTTP/HTTPS、本机或 IP 目标、自定义 API、各类受信任 raw 主机和重定向。核对配置未被失败操作覆盖、原始 URL 校验及 Token 边界仍有效、定时同步保留待处理状态；同步更新两份 README 的权限说明。

## 4. KDF 参数升级（建议第三批）

代码事实：MSYE1 的 Base64 载荷为 `5B magic + 16B salt + 12B IV + ciphertext（含 16B GCM tag）`；salt 随密文保存，迭代次数没有保存。`deriveKey` 对读写均固定使用 PBKDF2-HMAC-SHA256、310000 次、AES-GCM-256。直接替换常量会破坏旧密文读取。

资料核实：OWASP 当前列出 PBKDF2-HMAC-SHA256 为 600000 次。该建议面向密码存储，可作为本项目离线猜测成本的参考，不等于 E2E 协议必须直接换常量。[OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

本机实测（2026-09-20）：Windows、隔离 Edge 153.0.4234.32 扩展后台、合成口令。一次导入口令，每次派生使用新的随机 16B salt，交替测量两种迭代数，各预热 1 次、正式 7 次，绕过应用缓存。

| 迭代次数 | 单次派生中位耗时 | 最小—最大 |
| --- | --- | --- |
| 310000 | 53.7 ms | 49.9—56.9 ms |
| 600000 | 103.7 ms | 96.2—108.3 ms |

中位耗时为原来的 1.93 倍，详见 [原始数据与方法](validation/2026-09-20-security-plan/kdf-benchmark.json)。这只证明本机桌面 Edge 的派生耗时，不含压缩、加密、网络与整个同步流程，不代表 Firefox、手机或低性能设备。生产参数及密文格式未改。

建议两阶段切换：

1. **阶段 A：增加读取兼容，继续写 MSYE1。** MSYE1 永久固定按 310000 解密。候选 MSYE2 格式为 `5B magic + 4B 大端迭代数 + 16B salt + 12B IV + ciphertext/tag`，版本固定 PBKDF2-SHA256 与 AES-GCM-256，不增加算法选择框架。初版只接受批准的 600000 参数；未知版本、异常长度或参数在昂贵派生前拒绝，防止畸形输入驱动任意计算量。新格式头部作为 GCM additionalData 认证；保留缓存时身份必须区分版本、迭代数与 salt，并随锁定清除。
2. **阶段 B：用户明确切换 MSYE2 写入。** 所有同步设备均已升级读取能力、低性能设备实测可接受后才开放。复用现有候选文件、读回校验与设置提交机制；不批量重写旧备份，不删除旧密码对应历史。KDF 外层格式与空树内层格式的兼容性须分别满足，不能互相代替。

损失控制：候选验证失败不提交新设置；中断后继续或取消已有迁移。旧客户端读 MSYE2 应停止并提示升级，绝不回退明文。回退旧客户端需要其可读备份、对应密码及正确目标指针，不能仅把开关关掉。保留旧备份也意味着这些历史副本仍具有原有 KDF 强度。

验收：独立固定的 MSYE1 密文样例（不能只测同版自加密自解密）、MSYE2 固定样例、新旧混读、错误密码、头部及密文篡改、截断、参数边界、缓存隔离、迁移中断及旧客户端行为；阶段 B 前补 Firefox 与低性能/手机设备实测。没有这些证据不得把“本机约 104 ms”写成全平台通过。
